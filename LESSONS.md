## 2026-07-17 — WRH-55 — a growing test file's coverage-instrumented CI run started failing the required Unit tests check on unrelated tests

- What: `WorkOrdersPage.tsx`/`WorkOrdersPage.test.tsx` grew substantially (a new Tabs UI with two extra `Table` instances plus a detail `Modal`). `npm run test:coverage` (CI's "Unit tests" job, `v8` coverage provider, default vitest file-parallelism) started intermittently timing out 2-9 tests in that one file per run at the global 10000ms `testTimeout` - not the same tests each run, and not tests that do anything unusual (no rc-motion/Popconfirm involved, matching the CategoriesPage precedent this repo already had a fix for). The same file passed 22/22 locally without `--coverage`, and in isolation with `--coverage` (borderline, ~12-30s for the single heaviest test). CI failed it twice in a row (including after a full rerun), blocking `gh pr merge`'s required check.
- Fix: three changes, not one, applied across two rounds - (1) added `--no-file-parallelism` to the `test:coverage` npm script (`package.json`) to remove cross-file CPU contention during the coverage run, which explained most of the spread-across-tests failures (2-9 tests/run down to 1); (2) raised `vite.config.ts`'s global `testTimeout` 10000 -> 20000, because even with file-parallelism removed, individual tests in this specific heavier file could still occasionally cross 10s purely from `v8` coverage instrumentation overhead; (3) after (1)+(2) landed, CI still failed on the _one_ remaining heaviest test each run (confirmed via the actual GitHub Actions log, not just local reruns - local machine and CI runner have different headroom, so a test passing locally under the same flags doesn't guarantee it'll pass in CI) - two specific tests (`WorkOrdersPage.test.tsx`'s "does not show a loading state on other draft rows..." and "refreshes the Active tab after starting a WO from the Manage tab", the latter doing two full render/interact cycles) needed their own even-larger per-test override (45000ms/40000ms) on top of the global bump.
- Rule: when a page/test file grows meaningfully larger (new UI surface, more `Table`/`Modal` instances, more hooks), re-verify `npm run test:coverage` (the exact CI command, not just `npm test`) before considering the change done - don't assume passing `npm test` (no coverage) or an isolated coverage run of just that file is sufficient, since cross-file parallelism contention only shows up in the _full_ coverage run and can look like "random unrelated tests failing" rather than an obvious regression in the diff. If it's failing intermittently across multiple tests in one file (not consistently the same one), suspect resource contention (fix: `--no-file-parallelism` and/or raise the global timeout) rather than chasing it as N separate test-level bugs. Even after a local fix looks clean (including re-running the _exact_ CI command), don't assume CI will agree - CI's runner can be measurably slower than a local dev machine for the same flags, so treat a green local run as a strong signal, not proof, until CI itself confirms it; check the actual CI job log (`gh run view --job <id> --log-failed`), not just the checks summary, to see which specific test(s) are still borderline.

## 2026-08-16 — WRH-71 — a new clickable-table-row-opens-Modal detail view took 5 review rounds because each fix's own new code introduced the next finding

- What: `BoxesPage`'s box-detail view (click a row → `Modal` with a nested items `Table`, closable) went through 5 rounds of `/code-review` before landing clean, each round finding something real: (1) `useQuery`'s default `staleTime` let a reopened detail show minutes-old contents despite the code's own stated intent that it be fresh; (2) `onRow`'s `onClick`-only row activation had no keyboard/screen-reader path at all; (3)+(4), both introduced by round-2's own fix - adding `tabIndex`/`onKeyDown` to the row for keyboard access made a keyboard Enter/Space on a _nested_ interactive element (a "Print QR" button) bubble up and double-fire the row's handler too (mouse click didn't have this problem, since the button's `onClick` already called `stopPropagation`, but that doesn't stop the earlier `keydown` bubble), and separately the detail `Modal`'s loading spinner used `isLoading` instead of `isFetching`, so a `staleTime: 0` refetch on reopen didn't block the previous, stale item list from rendering first; (5) round-4's own fix for a title/content flash-on-close (deferring `detailBox` clearing to `Modal`'s `afterOpenChange` instead of clearing it synchronously in `onCancel`) introduced a race - closing box 1 then immediately opening box 2 before the close animation finished let the _earlier_ close's now-late `afterOpenChange(false)` callback wipe out box 2's just-set detail state.
- Fix: each finding got a targeted, one-line-ish fix (`staleTime: 0`; `tabIndex`+`onKeyDown` guarded by `event.target === event.currentTarget` so only the row's own keydown reacts, not a bubbled one from a descendant; `isFetching` in place of `isLoading`; a ref (`isDetailOpenRef`) checked inside `afterOpenChange` so a stale close-callback can't clear state a subsequent open already set) - no single fix was wrong, but none of them were anticipated up front because the initial plan only mapped the ticket's literal ACs/TCs (which said nothing about keyboard access, cache freshness, or close-animation timing) into code, not the general shape of "clickable row + Modal + async data fetch."
- Rule: before implementing a new "click a row/card to open a `Modal` with async-fetched detail" flow (this repo's now-recurring pattern - see `DashboardPage`'s stock-summary detail and `WorkOrdersPage`'s detail modals for prior instances), design in up front, not as review-driven patches: (a) an explicit `staleTime` on the detail query if "must reflect current state" is a requirement, not the app's default; (b) `isFetching`, not `isLoading`, driving any loading UI on a query whose cache can be reused across opens; (c) keyboard operability on the row (`tabIndex` + `onKeyDown` for Enter/Space) from the start if the row hosts an `onClick`, not added after a reviewer flags mouse-only interaction - and if the row also contains its own nested interactive elements (buttons/links), guard the row's key handler with `event.target === event.currentTarget` from the start, not after a reviewer finds the double-fire; (d) if a flash-of-stale-title/content on close motivates deferring state-clearing into an animation-completion callback (`afterOpenChange` or equivalent), guard it against a fresher open racing the stale close from the start (a ref holding the latest open/closed state, checked inside the callback) rather than discovering the race in a later review round.
